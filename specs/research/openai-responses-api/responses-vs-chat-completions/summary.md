# Responses API vs Chat Completions

## Bottom Line

Chat Completions *can* set thinking level. `reasoning_effort` accepts the same values as Responses' `reasoning.effort` (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, varying by model). For a plain request with no tools, effort works on every OpenAI model that Chat Completions serves. Responses is required in four cases:

1. **Pro models.** Every `*-pro` model ID is Responses-only, and GPT-5.6 and GPT-6 replace pro IDs with `reasoning.mode: "pro"`, which only Responses has.
2. **Reasoning combined with function tools on GPT-5.4 and newer.** Chat Completions returns 400 `Function tools with reasoning_effort are not supported for <model> in /v1/chat/completions`. GPT-6 Astra and 6.1 Sol have no Chat Completions tool calling at all.
3. **Reasoning summaries and any visible reasoning output.** Chat Completions returns only a reasoning-token count.
4. **Carrying reasoning across turns or tool calls.** This includes encrypted reasoning items for stateless use, `reasoning.context` and `configuration_update`.

Chat Completions is not deprecated and still receives new models, but new reasoning features ship only to Responses. Responses works fully without server-side state (`store: false` plus replaying the returned items, including `encrypted_content`).

## Key Findings

- **The effort value set is the same in both APIs. Only the shape differs** (`reasoning_effort` vs `reasoning: {effort}`). Accepted values depend on the model: GPT-6 Astra and 6.1 Sol reject `none` (HTTP 400); `max` exists only on GPT-5.6 and GPT-6; `minimal` exists only on gpt-5 era models. Defaults also differ: gpt-5.1, 5.2 and 5.4 default to `none`, while gpt-5.5, 5.6 and 6.x default to `medium`. — [SDK ReasoningEffort](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/shared/reasoning_effort.py), [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning), [model-matrix.md](./model-matrix.md)
- **Reasoning plus tools is blocked on Chat Completions from GPT-5.4 on.** The migration guide says: "Starting with GPT-5.4, Chat Completions does not support tool calling with `reasoning_effort` values other than `none`." The GPT-6 Sol and Luna pages say Chat Completions "supports function calling only with `reasoning_effort` set to `none`", and Astra and 6.1 Sol need Responses for any tool calling. Field reports confirm this for gpt-5.4, 5.5, 5.6-sol/terra/luna, 6-sol and 6.1-sol ([pipecat#4043](https://github.com/pipecat-ai/pipecat/issues/4043), [OpenAI forum](https://community.openai.com/t/gpt-5-6-chat-completion-reasoning-effort-bug-behavior-change/1386454), [frigate#24555](https://github.com/blakeblackshear/frigate/discussions/24555)). The GPT-5.4, 5.5 and 5.6 model pages themselves do not mention it. Structured output through `response_format` is not documented as restricted, but **structured output done as a forced tool call is a tool call** and would hit the 400. — [migration guide](https://developers.openai.com/api/docs/guides/migrate-to-responses), [latest-model guide](https://developers.openai.com/api/docs/guides/latest-model)
- **Responses-only models.** Pro IDs gpt-5-pro, gpt-5.2-pro, gpt-5.4-pro, gpt-5.5-pro and o3-pro are each "Chat Completions: Not supported". Codex, deep-research and computer-use IDs are also Responses-only. Kiln lists `gpt-5.2-pro` and `gpt-5.4-pro`. — [gpt-5.4-pro page](https://developers.openai.com/api/docs/models/gpt-5.4-pro.md), [SDK ResponsesModel](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/shared/responses_model.py)
- **Reasoning features that only Responses has:** `reasoning.summary` (auto/concise/detailed; opt-in; may need org verification), `reasoning.mode` (pro), `reasoning.context` (persisted reasoning across turns, default `all_turns` on GPT-5.6), `encrypted_content` on reasoning items, `configuration_update` items (GPT-6), and the `phase` field on assistant messages (GPT-5.4/5.5 tool-heavy flows). The Chat Completions message type has no reasoning field. — [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning), [SDK chat message](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/chat/chat_completion_message.py)
- **Structured output** moves from `response_format.json_schema{...}` to a flattened `text.format{type, name, schema, strict}`. Both APIs support it fully. — [migration guide](https://developers.openai.com/api/docs/guides/migrate-to-responses), [structured outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs.md)
- **Tool calling** changes shape in Responses. Tools are internally tagged (`{type, name, parameters, strict}`); calls are `function_call` items, and results go back as `function_call_output` items matched by `call_id`. **Responses tries strict mode by default; Chat Completions is non-strict by default.** — [function calling guide](https://developers.openai.com/api/docs/guides/function-calling.md)
- **Logprobs:** Chat Completions uses `logprobs`/`top_logprobs`; Responses uses `include: ["message.output_text.logprobs"]` plus `top_logprobs`. Neither API allows logprobs, `temperature` or `top_p` when effort is not `none`. — [latest-model guide](https://developers.openai.com/api/docs/guides/latest-model)
- **Streaming:** Chat Completions streams `delta` chunks, with usage only through `stream_options.include_usage`. Responses streams typed SSE events (`response.output_text.delta`, `response.function_call_arguments.delta`, `response.reasoning_summary_text.delta`, `response.output_item.done`, `response.completed`, ...). — [SDK stream events](https://raw.githubusercontent.com/openai/openai-python/main/src/openai/types/responses/response_stream_event.py)
- **Usage:** both APIs report the same information under different names. `prompt_tokens`/`completion_tokens`/`*_details.reasoning_tokens` become `input_tokens`/`output_tokens`/`output_tokens_details.reasoning_tokens`. Cache read and write counts exist in both. A token-limit stop is `finish_reason: "length"` in Chat Completions and `status: "incomplete"` with `incomplete_details.reason: "max_output_tokens"` in Responses. Responses has no `n`.
- **State:** Responses stores by default (`store` defaults to true, 30-day retention). `previous_response_id` and Conversations are optional and do not reduce input billing. Stateless use is first-class: `store: false` plus replaying all output items. ZDR organizations get `store: false` enforced. — [migration guide §3–4](https://developers.openai.com/api/docs/guides/migrate-to-responses), [conversation state](https://developers.openai.com/api/docs/guides/conversation-state.md)
- **Chat Completions is not deprecated.** It is absent from the deprecations page, and GPT-5.4, 5.5, 5.6 and 6.x all ship to it. The docs say "remains supported, Responses is recommended for all new projects." In practice it is falling behind for reasoning plus tools. — [chat-completions-status.md](./chat-completions-status.md)

## Open Questions / Gaps

- **What happens when a GPT-5.5+ model gets tools on Chat Completions with no `reasoning_effort` at all?** A third-party gateway ([APIYI](https://docs.apiyi.com/en/api-capabilities/openai/responses-migration.md), secondary source) reports that omitting the parameter avoids the 400 and tools work. Those models default to `medium`, so it is unclear whether they then reason or silently drop to `none`. The same source also reports "no error, but the tool is never called" on some routes. OpenAI does not document this case.
- **Is GPT-5.2 or earlier affected?** OpenAI's wording ("Starting with GPT-5.4") excludes it. One issue ([ruby_llm#785](https://github.com/crmne/ruby_llm/issues/785)) claims gpt-5 through 5.2 and the o-series also reject the combination. I found no corroboration, so this is unverified.
- **`tool_choice` forcing on Chat Completions with effort `none`.** I did not check whether a forced tool call (Kiln-style structured output through a tool) behaves differently from `auto`.
- I did not find the o3/o4-mini/o1 effort lists on the extracted model pages. The extracts were reranked chunks that cut that line.
- The migration guide's capability table lost its check marks during extraction. I relied on the prose and the SDK types instead.
- `developers.openai.com` is blocked by this session's egress proxy, so every OpenAI doc was read through Tavily extract. Undated live pages reflect 2026-10-05.
- Azure OpenAI, OpenRouter and other hosts may behave differently. That is out of scope here (see the "LiteLLM Responses support" and "Justification check" subtopics).
