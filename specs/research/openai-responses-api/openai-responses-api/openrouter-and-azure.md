# OpenRouter and Azure OpenAI

Brief by design: the research plan asks only how these two routes serve OpenAI models. Fetched 2026-10-30.

## OpenRouter

### How OpenRouter serves OpenAI models on its Chat Completions endpoint

OpenRouter does not state in so many words "we call OpenAI's `/v1/responses` upstream". Three things in its docs point that way:

1. Its reasoning-detail formats include `"openai-responses-v1"` ("OpenAI responses format version 1") and `"azure-openai-responses-v1"`, used to tag reasoning blocks returned on **Chat Completions** responses (`choices[].message.reasoning_details`). ([OpenRouter Reasoning Tokens](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens))
2. On mid-conversation effort changes: "OpenRouter normalizes each into one internal representation and re-emits it in the form the selected provider accepts. A Responses `configuration_update` sent to a Claude model becomes a per-message `output_config`, and a Chat Completions or Messages API update sent to an OpenAI model becomes a Responses `configuration_update` item." It also says "The Chat Completions form is an OpenRouter extension, since OpenAI's own Chat Completions API has no per-message equivalent." (same page)
3. `reasoning.mode` (pro): "only supported by OpenAI GPT-5.6 and newer, when served by OpenAI or Azure" and OpenRouter accepts it on its Chat Completions shape too. Pro mode exists only on OpenAI's Responses API. (same page)

**Inference:** OpenRouter translates Chat Completions requests for OpenAI reasoning models into OpenAI Responses requests upstream. That is why the tools-plus-reasoning restriction does not hit Kiln's OpenRouter route for the same models. OpenRouter carries OpenAI's encrypted reasoning back to the client as `reasoning_details` entries of `type: "reasoning.encrypted"` and expects them echoed unchanged: "When providing reasoning_details blocks, the entire sequence of consecutive reasoning blocks must match the outputs generated by the model during the original request; you cannot rearrange or modify the sequence of these blocks." (same page)

**How to confirm:** OpenRouter has a debug flag that returns the exact upstream body. "`echo_upstream_body?: boolean; // If true, returns the transformed request body sent to the provider`". "The debug option only works with streaming mode (`stream: true`)." On Chat Completions it arrives as the first chunk, with empty `choices` and a `debug` field. ([OpenRouter errors and debugging](https://openrouter.ai/docs/api_reference/errors-and-debugging)) Not run here (needs an OpenRouter key).

Other OpenRouter facts relevant to Kiln:

- Effort values accepted: `"max"`, `"xhigh"`, `"high"`, `"medium"`, `"low"`, `"minimal"`, `"none"`; per-model supported values are discoverable from `GET /api/v1/models` (`reasoning.supported_efforts`, `default_effort`, `mandatory`). ([Reasoning Tokens](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens))
- `reasoning.context` is "only supported by OpenAI GPT-5.6 and newer". (same)
- Encrypted reasoning "may appear as `[REDACTED]` in streaming responses". (same)
- Third-party evidence that reasoning replay through OpenRouter's Chat Completions shape is fragile: a pi-mono issue measured "0/290 multi-turn tool-loop trials with replay across `anthropic/claude-opus-5`, `openai/gpt-5.6-sol`, `moonshotai/kimi-k3`" through OpenRouter chat completions versus "105/105 (gpt-5.6-sol)" through `openai-responses`, partly due to their client and partly "a server-side component on OpenRouter's end (reasoning dropped when co-located with tool-call chunks — filed internally)". ([earendil-works/pi #7994](https://github.com/earendil-works/pi/issues/7994), third-party, undated in the excerpt) The requests themselves succeeded; only reasoning replay failed.

### OpenRouter's own Responses API

> "OpenRouter's Responses API provides OpenAI-compatible access to multiple AI models through a unified interface, designed to be a drop-in replacement for OpenAI's Responses API."
>
> "Stateless Only: This API is stateless - each request is independent and no conversation state is persisted between requests. You must include the full conversation history in each request. Requests that set `store: true` or a non-null `previous_response_id` are rejected with a `400` error."
> — [OpenRouter Responses API](https://openrouter.ai/docs/api_reference/responses/overview)

Its reasoning doc shows replaying a reasoning item with `id`, `encrypted_content`, and `summary`, plus `include: ["reasoning.encrypted_content"]`. ([Reasoning Tokens](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens))

**Implication for Kiln (inference):** Kiln's OpenRouter route already works through Chat Completions and does not need to change for this project. If Kiln ever moved OpenRouter to Responses, it would have to send `store: false` (or omit it, since `true` is rejected) and could not use `previous_response_id`.

## Azure OpenAI (Microsoft Foundry)

- Responses is available on the v1 API: `https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/responses`. "The v1 API is required to access the latest features." Microsoft recommends Responses: "For Azure OpenAI models we recommend using the Responses API". ([Use the Azure OpenAI Responses API](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/responses), [v1 API lifecycle](https://learn.microsoft.com/en-us/azure/foundry/openai/api-version-lifecycle))
- Supported models on Responses include `gpt-6.1-terra`, `gpt-6.1-sol`, `gpt-6-luna`, `gpt-6-sol`, `gpt-6-astra`, the `gpt-5.6-*` family, `gpt-5.5`, `gpt-5.4*` including `gpt-5.4-pro`, `gpt-5.2`, `gpt-5.1*`, `gpt-5*`, `gpt-4.1*`, `gpt-4o*`, `o1`, `o3`, `o3-mini`, `o4-mini`, and others; "Not every model is available in every supported region." `model` is the Azure deployment name. ([Use the Azure OpenAI Responses API](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/responses))
- The same Chat Completions restriction exists on Azure, with the same error text: "The `gpt-5.6` models support the Chat Completions API and tools, but can't combine reasoning with tools on Chat Completions." Error: "`Function tools with reasoning_effort are not supported for gpt-5.6-sol in /v1/chat/completions. To use function tools, use /v1/responses or set reasoning_effort to 'none'.`" ([Azure reasoning models](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning))
- Stored responses: "By default, response data is retained for 30 days." ([Use the Azure OpenAI Responses API](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/responses))
- Stateless reasoning: same as OpenAI now: "In stateless mode, reasoning items in the response's `output` array include an `encrypted_content` property by default... the API still accepts `reasoning.encrypted_content` in the `include` parameter for compatibility, but no longer requires it." ([Azure reasoning models](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning)) Microsoft's C# sample adds: "Don't use PreviousResponseId when not stored." ([Responses how-to](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/responses))
- **Known gap vs OpenAI (third-party evidence):** Azure appears to reject replayed reasoning items that carry an `id` when `store: false`, even with `encrypted_content` present ("Item with id 'rs_...' not found. Items are not persisted when `store` is set to false"). Codex sends `store: true` to Azure for this reason; stripping input item ids also works. ([openai/codex #35739, 2026-07-28](https://github.com/openai/codex/issues/35739)) See [reasoning-and-state.md](./reasoning-and-state.md#what-happens-when-a-reasoning-item-is-replayed-by-id-with-store-false).
- Azure says `reasoning.context` `all_turns` works on GPT-5.4 and GPT-5.5 as well; OpenAI's page names only GPT-5.6 and GPT-6.1 Sol. (Discrepancy noted in [reasoning-and-state.md](./reasoning-and-state.md).)
- Azure footnotes on Chat Completions with reasoning models: "Reasoning models will only work with the `max_completion_tokens` parameter when using the Chat Completions API. Use `max_output_tokens` with the Responses API." "Parallel tool calls are not supported when `reasoning_effort` is set to `minimal`." ([Azure reasoning models](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning))
