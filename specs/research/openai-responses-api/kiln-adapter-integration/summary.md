# Kiln adapter integration

## Bottom Line

Kiln doesn't need a new Responses code path. LiteLLM 1.102.0 (the pinned version) already has a completion→Responses bridge that returns chat-shaped objects. Kiln is **already using it without knowing**: for `gpt-5.4-pro` / `gpt-5.2-pro`, and for every gpt-5.4+ / gpt-6 call on OpenAI that carries a function tool with reasoning on. The smallest complete change is a per-model `KilnModelProvider` flag. Inside `LiteLlmAdapter`, the flag would (1) force the bridge with an `openai/responses/<model>` model id, (2) ask for a reasoning summary and pick a `store` policy, and (3) fix a `choices[0]`-only read that drops tool calls when a bridged response holds both text and a tool call. That is about 1–2 days, with no `BaseAdapter`, trace or streaming-contract changes. Calling `litellm.aresponses()` directly would mean re-implementing the bridge, including converting Responses SSE events into the `ModelResponseStream` chunks that `BaseAdapter.invoke_openai_stream` publicly yields. That is roughly 1.5–3 weeks. Separately, the reason Kiln turned function calling off on 9 gpt-5.4+ OpenAI entries was that LiteLLM had no automatic routing at the time (1.81.16). That routing exists from 1.82.2, so the reason no longer holds.

## Key Findings

- **LiteLLM routes some `completion()` calls to `/v1/responses` on its own.** It bridges when (a) LiteLLM's model map says `mode: "responses"` (pro and codex models), (b) the model name has a `responses/` prefix, (c) the global `route_all_chat_openai_to_responses` is set, or (d) for OpenAI/Azure GPT-5-family names, there is a function tool with reasoning on (gpt-5.4+, including gpt-6*), or `reasoning_effort` plus `reasoning_summary`. Source: `.venv/.../litellm/main.py:1047-1135`, `5596-5650`. Probe table: [bridge-probe-results.md §1](./bridge-probe-results.md).
- **Kiln's "until Kiln routes these models to /v1/responses" flags are stale at the pinned version.** `supports_function_calling=False` was added when `uv.lock` had litellm 1.81.16 (commit `985d9616`). Automatic gpt-5.4+ tools routing first appears in litellm **1.82.2** (released 2026-03-13; checked by diffing PyPI wheels). The flags were copied to `ml_model_list.py:824, 884, 974, 1065, 1122, 1181, 1240, 1296, 1397`. Not yet confirmed against real OpenAI.
- **End-to-end probe: the unmodified adapter works through the bridge.** Tool loop, json_schema → `text.format`, the forced `task_response` tool, reasoning-summary capture, usage, cached tokens, cost, and AI SDK streaming events were all correct against a fake Responses server. [bridge-probe-results.md §2](./bridge-probe-results.md).
- **Real bug (non-streaming):** when one Responses reply holds both a text message and a function call, the bridge returns two choices. Kiln reads only `choices[0]` (`libs/core/kiln_ai/adapters/model_adapters/litellm_adapter.py:443-457`), so the preamble text became the final output and the tool never ran. Streaming is fine, because `stream_chunk_builder` merges the chunks. This already affects bridged pro models.
- **What automatic bridging misses:** no-tool requests whose parameters only Responses accepts. Example: effort `max` on gpt-6.1-sol, which Kiln left out for that reason (`ml_model_list.py:549-553`). Probe scenario 4 confirmed that request goes to `/chat/completions`. Also unmapped pro models (`gpt-6-sol-pro`), and reasoning text: the bridge sends `reasoning: {effort}` with no `summary`, so OpenAI returns no reasoning text unless Kiln asks.
- **Two one-line levers force the bridge per request:** model id `openai/responses/<id>` (or `azure/responses/<deployment>`), or `reasoning_summary: "auto"` in the request body. Both were checked in the probe, and the second also asks for summaries.
- **The bridge doesn't map logprobs, and has no `store` default.** Logprobs: probe scenario 7 hit Kiln's "Logprobs were required" error. Low impact, since no GPT-5.x/6 entry supports logprobs. `store`: the bridge sends no `store` field, so OpenAI's Responses default applies. That retention change is for subtopic 1 to confirm. `store: false` + `include: ["reasoning.encrypted_content"]` pass straight through, and encrypted reasoning round-trips inside a non-streaming tool loop. Streaming drops `reasoning_items` between tool rounds. Saved traces never keep them (`litellm_adapter.py:965-1017`).
- **Every Chat-Completions touchpoint is mapped:** message building, both tool loops (`litellm_adapter.py:147-276`, `adapter_stream.py:212-313`), structured output modes (`:462-559`), logprobs (`:408-426`, `:794-796`), reasoning capture (`:428-441`), usage and cost (`:812-849`), prompt caching (`:752-758`), streaming contract (`base_adapter.py:381-400, 857-983`), traces (`:965-1042`). Full table: [adapter-touchpoints.md](./adapter-touchpoints.md).
- **How to opt in without touching `BaseAdapter`:** add `openai_responses_api: bool = False` to `KilnModelProvider` (`ml_model_list.py:368`), validated to openai/azure_openai like `openrouter_reasoning_object`. It is read only in `LiteLlmAdapter.litellm_model_id` / `build_extra_body` / the choice-reading helper. Don't use the global `route_all_chat_openai_to_responses`: Kiln maps custom / OpenAI-compatible / Ollama providers to LiteLLM's `openai` provider (`libs/core/kiln_ai/utils/litellm.py:91-93`), so the global would break them.

## Open Questions / Gaps

- **No real OpenAI calls.** The probes used a fake server, so they verify Kiln↔LiteLLM translation only. A paid run is still needed to confirm that OpenAI accepts the bridged requests: `strict: null` on function tools, `summary` with effort `none`, reasoning items sent back by id without `store: false`, and `max` on gpt-6.1-sol via Responses.
- Whether real GPT-5.x/6 models emit a text message and a function call in the same response, which would trigger the `choices[0]` bug. That is API behaviour (subtopic 1). The Kiln-side fix is cheap either way.
- Whether Responses refusals (`refusal` content parts) reach `message.refusal`, which `raise_for_empty_model_response` checks. I didn't trace this.
- Azure: Kiln's `azure_openai` entries are o-series and GPT-4.x only. The bridge's automatic check for Azure uses the deployment name, so a forced `azure/responses/` prefix would be needed. Not probed.
- The effort estimates are inference from code size, not a prototype.
