# Prior art: how other frameworks call OpenAI's Responses API

Per-framework notes. Each section covers: the architecture choice (conversion from a chat-shaped history, or a native path), how reasoning items move between turns, the `store` default, how a reply with text plus tool calls is represented, streaming, and the bugs that followed.

## Comparison at a glance

| | History format the framework stores | Path to Responses | `store` sent by default | Reasoning carried between turns | Text + tool calls in one reply |
|---|---|---|---|---|---|
| Agents SDK | Responses input items (canonical) | Native. Chat Completions is the converted path | Omitted (server default, true) | Reasoning items replayed with their `id`; opt-in `reasoning_item_id_policy="omit"` strips ids | Separate items; one model turn |
| AI SDK | Own neutral message parts + per-part provider metadata (`itemId`, `reasoningEncryptedContent`, `phase`) | Separate Responses model that converts from the neutral format; default since `@ai-sdk/openai` 2.0.0 | `true` (sets it explicitly) | `store:true`: `item_reference` by id. `store:false`: full item + encrypted content, auto `include` | One assistant message with text and tool-call parts |
| Pydantic AI | Own neutral `ModelResponse` parts; `ThinkingPart` holds `id` + `signature` (encrypted content) | Separate `OpenAIResponsesModel`; default for `openai:` since v2.0.0 | Omitted (server default) | Always requests encrypted content for reasoning models; replays `id` + `encrypted_content` + summary; `openai_send_reasoning_ids=False` escape hatch | One `ModelResponse` with `TextPart`s and `ToolCallPart`s |
| LangChain | `AIMessage` (chat-shaped: content + `tool_calls`), extended with Responses content blocks | Same `ChatOpenAI` class, routes per request by feature detection; converts `AIMessage` to items | Omitted unless set | Replays reasoning blocks with ids; `store=False` drops ids and bare reasoning, keeps encrypted | One `AIMessage` with text blocks and `tool_calls` |
| LlamaIndex | `ChatMessage` with blocks (`TextBlock`, `ToolCallBlock`, `ThinkingBlock`) | Separate `OpenAIResponses` class; converts blocks to items | `False` | `store=False`: reasoning dropped. `store=True`: reasoning sent by id with summary only | One `ChatMessage`; serializer once dropped the text |
| Continue | Chat-shaped `ChatMessage`s; separate "thinking" messages carry reasoning details | Converter `toResponsesInput` + a sanitizer pass | Omitted | Requests encrypted content; sanitizer drops reasoning without it and strips ids from the items after it | Assistant message with `toolCalls` |
| Haystack | `ChatMessage` with texts, tool calls, `ReasoningContent.extra` (raw item fields) | Separate `OpenAIResponsesChatGenerator` | Omitted | Replays reasoning with `id` and `encrypted_content` if the user asked for it | One `ChatMessage`; converted order is reasoning, then function calls, then text |
| DSPy | Chat-shaped request | Builds a Responses payload and calls LiteLLM's native `litellm.responses()` | Not set | Not applicable: DSPy does single calls | Parsed from output items |

## OpenAI Agents SDK (Python)

**Architecture: native path, Responses items are the canonical history.** The docs list the Responses model as "Recommended" and Chat Completions as the second flavor ([docs/models/index.md](https://github.com/openai/openai-agents-python/blob/cd26bbbc52847845fde73b9952b51e62e2bcbdc0/docs/models/index.md)). The run loop keeps history as Responses input items (`TResponseInputItem`). Chat Completions is the converted path: `Converter.items_to_messages` turns items into chat messages, and `Converter.message_to_output_items` turns a chat reply back into items ([chatcmpl_converter.py L123, L548](https://github.com/openai/openai-agents-python/blob/cd26bbbc52847845fde73b9952b51e62e2bcbdc0/src/agents/models/chatcmpl_converter.py#L548)). This is the reverse of the conversion Kiln is considering.

**Text plus tool calls.** On the chat side, the converter's rule is stated in its docstring: "tool calls get attached to the *current* assistant message, or create one if none." A chat reply becomes, in order: one reasoning item (if any), one message item, then one `function_call` item per tool call. Items made from chat data get the placeholder id `__fake_id__` ([fake_id.py](https://github.com/openai/openai-agents-python/blob/cd26bbbc52847845fde73b9952b51e62e2bcbdc0/src/agents/models/fake_id.py)), and `_remove_openai_responses_api_incompatible_fields` strips that id and any `provider_data` before sending to Responses, and drops reasoning items that came from other providers ([openai_responses.py L1075](https://github.com/openai/openai-agents-python/blob/cd26bbbc52847845fde73b9952b51e62e2bcbdc0/src/agents/models/openai_responses.py#L1075)).

**Store and reasoning.** `store` is passed only when the user sets it (`"store": self._non_null_or_omit(model_settings.store)`, [L1052](https://github.com/openai/openai-agents-python/blob/cd26bbbc52847845fde73b9952b51e62e2bcbdc0/src/agents/models/openai_responses.py#L1052)), so the server default applies. Encrypted reasoning is opt-in through `response_include`. The docs say: "For stateless `store=False` calls, request `reasoning.encrypted_content` in the response, then include those reasoning items as input in the next request" ([models/index.md L150](https://github.com/openai/openai-agents-python/blob/cd26bbbc52847845fde73b9952b51e62e2bcbdc0/docs/models/index.md)).

**Bugs after shipping.**
- Repeated 400s `Item 'rs_...' of type 'reasoning' was provided without its required following item`: [#985](https://github.com/openai/openai-agents-python/issues/985) (2025-07, code interpreter + handoff; maintainer first called it server-side), [#1611](https://github.com/openai/openai-agents-python/issues/1611) (2025-08, with `previous_response_id`), [#1660](https://github.com/openai/openai-agents-python/issues/1660) (2025-09, GPT-5 + tools), [#2503](https://github.com/openai/openai-agents-python/issues/2503) (2026-02, nested handoff history sent an orphan reasoning item).
- The maintainer's answer (2026-03-13 on #1660) was a new opt-in setting: "With the `reasoning_item_id_policy="omit"`, your apps should be able to avoid the 400 errors mentioned here... This is still opt-in, but if things go pretty well for all users, we may consider switching the default to "omit" in future releases." The docs describe it as: "keeps the reasoning content but strips the reasoning item `id`" ([running_agents.md](https://github.com/openai/openai-agents-python/blob/cd26bbbc52847845fde73b9952b51e62e2bcbdc0/docs/running_agents.md)). The JS SDK got the same option (`reasoningItemIdPolicy`, [openai-agents-js#929](https://github.com/openai/openai-agents-js/issues/929), v0.4.13).
- [PR #3207](https://github.com/openai/openai-agents-python/pull/3207) (merged 2026-05-08): when the runner drops a tool call that has no output, it now also drops the reasoning item before it, because "the Responses API rejects reasoning items that are not followed by their associated model-emitted item."
- ZDR: [#605](https://github.com/openai/openai-agents-python/issues/605) (2025-04) `Item with id 'rs_REDACTED' not found. Items are not persisted for Zero Data Retention organizations.` An OpenAI collaborator closed it a day later: "Just deployed the fix for this for ZDR orgs". The thread does not say what changed.

**Streaming.** The Responses model yields OpenAI's stream events unchanged. The Chat Completions model converts chat chunks into Responses events (`ChatCmplStreamHandler`, [chatcmpl_stream_handler.py](https://github.com/openai/openai-agents-python/blob/cd26bbbc52847845fde73b9952b51e62e2bcbdc0/src/agents/models/chatcmpl_stream_handler.py)). The canonical stream shape is Responses events.

## Vercel AI SDK (`@ai-sdk/openai`)

**Architecture: neutral message format, two separate model classes.** `openai(modelId)` returns the Responses model; `openai.chat()` and `openai.responses()` pick explicitly ([openai-provider.ts](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/openai-provider.ts)). The default switched in `@ai-sdk/openai` 2.0.0 (AI SDK 5, published 2025-07-31): changelog entry "cc62234: chore (provider/openai): switch default to openai responses api" ([CHANGELOG.md](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/CHANGELOG.md)). Both endpoints convert from the AI SDK's own prompt format. Responses-specific data rides on each part as provider metadata: `itemId`, `reasoningEncryptedContent`, `phase`, `namespace`.

**Store and reasoning.** The converter is called with `store: openaiOptions?.store ?? true` ([openai-responses-language-model.ts L433](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/responses/openai-responses-language-model.ts#L433)). With `store` true, stored reasoning, assistant text, and provider-executed tool calls are sent as `{ type: 'item_reference', id }` "to reduce payload size". With `store === false` on a reasoning model, the SDK adds `include: ['reasoning.encrypted_content']` itself ([L590](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/responses/openai-responses-language-model.ts#L590)), sends full reasoning items, and drops reasoning that has no encrypted content with the warning "Reasoning parts without encrypted content are not supported when store is false" ([convert-to-openai-responses-input.ts L1833](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/responses/convert-to-openai-responses-input.ts#L1833)). A reasoning part with no id but with encrypted content is sent as an id-less reasoning item; changelog 5e18272 (3.0.35, 2026-02-26): "The OpenAI Responses API accepts reasoning items without an `id` when `encrypted_content` is supplied."

**Text plus tool calls.** One assistant message holds reasoning, text, and tool-call parts in order. Each part becomes its own item. Plain client-executed function calls are always sent as full `function_call` items without an `id`, never as `item_reference`. The source comment explains why: the matching `function_call_output` "can only reference the call by `call_id`... Sending either breaks call/output pairing and makes follow-up requests fail with 'No tool call found for function call output with call_id'" ([L949](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/responses/convert-to-openai-responses-input.ts#L949)). Assistant text is sent by reference only when reasoning precedes it in the same message ([L729](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/responses/convert-to-openai-responses-input.ts#L729)), because of the error in the next list.

**Tool schema strictness.** Changelog 2abd503 (4.0.77, 2026-09-25): "Default OpenAI Responses function tools to `strict: false` when tool strict mode is omitted." The code sends `strict: tool.strict ?? false` ([openai-responses-prepare-tools.ts L686](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/responses/openai-responses-prepare-tools.ts#L686)). The changelog shows several earlier flips of strict defaults (efc3a62, 52ce942, 73d9883).

**Finish reason.** Responses has no `tool_calls` finish reason. The SDK derives it: `hasFunctionCall ? 'tool-calls' : 'stop'` when there is no incomplete reason ([map-openai-responses-finish-reason.ts](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/responses/map-openai-responses-finish-reason.ts)).

**Streaming.** Responses SSE events are mapped to AI SDK stream parts (`text-start`/`text-delta`, `reasoning-start`/`reasoning-delta`/`reasoning-end`, `tool-input-start`/`tool-input-delta`, `tool-call`). Each reasoning summary part gets its own stream id `${itemId}:${summary_index}` ([L2812](https://github.com/vercel/ai/blob/dfed8e8234b684c3e2a0571ad1a1078c8364b44c/packages/openai/src/responses/openai-responses-language-model.ts#L2812)). The summary index stays inside the reasoning part's id; it never becomes a message or choice index.

**Bugs after the default switch** (selected; all on the vercel/ai tracker):
- [#7099](https://github.com/vercel/ai/issues/7099) (2025-07-07, AI SDK 5 beta): reasoning + tool call gives `Item 'rs_...' of type 'reasoning' was provided without its required following item`. The reporter's workaround was `openai.chat()`.
- [#8315](https://github.com/vercel/ai/issues/8315) (2025-08-27): `store:false` gives `Item with id 'rs_...' not found. Items are not persisted when store is set to false.` Maintainer: encrypted content "is required when using reasoning without store". This led to the automatic `include` (edc5548, 3.0.0).
- [#8216](https://github.com/vercel/ai/issues/8216) (2025-08-22): `No tool call found for function call output with call_id`. Fixed by [PR #11114](https://github.com/vercel/ai/pull/11114) (2025-12, "don't use item_reference for client-executed tool calls"). The same error came back with `previousResponseId` in [#18537](https://github.com/vercel/ai/issues/18537) (2026-08-06).
- [#8321](https://github.com/vercel/ai/issues/8321) (2025-08-27): dropping incomplete tool calls left an orphan reasoning item. Closed 2026-08-26 as no longer reproducible: "This suggests that OpenAI changed how it handles reasoning items whose related function call is no longer present."
- [PR #10827](https://github.com/vercel/ai/pull/10827) (2025-12-03): with `store:true`, a tool call that failed validation had no `itemId`, so its reasoning `item_reference` became unpaired: `Item 'fc_xxx' of type 'function_call' was provided without its required 'reasoning' item`. Root cause was fixed in #10733.
- [#10060](https://github.com/vercel/ai/issues/10060) (2025-11-07): ZDR orgs get `Item with id 'rs_...' not found. Items are not persisted for Zero Data Retention organizations.` Resolved by setting `store: false`.
- [#10573](https://github.com/vercel/ai/issues/10573) (2025-11-25) and [#13307](https://github.com/vercel/ai/issues/13307) (2026-03-10): `Duplicate item found with id rs_...` / `fc_...`.
- Changelog 216e2c9 (4.0.93, 2026-10-13): "pruning reasoning ... caused follow-up requests to fail with 'Item 'msg_...' of type 'message' was provided without its required 'reasoning' item'."

**Downstream fallout from the default switch.** Many apps on the AI SDK hit the ZDR error and fixed it by setting `store: false`: Supabase ([commit d29fbf6](https://github.com/supabase/supabase/commit/d29fbf6eb78deb642c7db9a48df10c6115b54b32), 2026-03), Langfuse ([PR #16810](https://github.com/langfuse/langfuse/pull/16810)), Twenty ([#20877](https://github.com/twentyhq/twenty/issues/20877), fixed 2026-06-22), Mastra ([#10860](https://github.com/mastra-ai/mastra/issues/10860)), opencode ([#2966](https://github.com/anomalyco/opencode/issues/2966), [#4426](https://github.com/anomalyco/opencode/issues/4426)), Lightdash ([#19771](https://github.com/lightdash/lightdash/issues/19771)). The Langfuse PR states the cost: "Requests carry the encrypted reasoning of earlier steps (a few KB per step)." One app, Coder Blink, switched back to Chat Completions instead ([coder/blink#34](https://github.com/coder/blink/issues/34), 2025-10): an interrupted stream left a reasoning part without its successor.

## Pydantic AI

**Architecture: neutral message format, two model classes, default flipped late.** `OpenAIChatModel` and `OpenAIResponsesModel` both convert from Pydantic AI's `ModelMessage` types. The bare `openai:` prefix switched to Responses in v2.0.0 (2026-06-23). It was announced with a deprecation warning in [PR #5334](https://github.com/pydantic/pydantic-ai/pull/5334) (merged 2026-05-13) and flipped in #5469 ([docs/changelog.md](https://github.com/pydantic/pydantic-ai/blob/79e157e8b7bbea20d2354740e981478dd54dbb23/docs/changelog.md)). `openai-chat:` keeps Chat Completions. The docs now say: "Use Responses whenever you need reasoning and tools together" ([docs/models/openai.md](https://github.com/pydantic/pydantic-ai/blob/79e157e8b7bbea20d2354740e981478dd54dbb23/docs/models/openai.md)).

**Reasoning.** For models whose profile supports it, `_build_include` always adds `reasoning.encrypted_content` on create ([openai.py L4274](https://github.com/pydantic/pydantic-ai/blob/79e157e8b7bbea20d2354740e981478dd54dbb23/pydantic_ai_slim/pydantic_ai/models/openai.py#L4274)). A `ThinkingPart` stores the reasoning item `id`, the summary text, and the encrypted content as `signature`. On replay it becomes a reasoning item with `id`, `encrypted_content`, and `summary`. `store` is only sent when set ([`_resolve_store`, L4236](https://github.com/pydantic/pydantic-ai/blob/79e157e8b7bbea20d2354740e981478dd54dbb23/pydantic_ai_slim/pydantic_ai/models/openai.py#L4236)). By default it also sends `reasoning.context="all_turns"` on models that support it.

**Escape hatch.** `openai_send_reasoning_ids` ([L1221](https://github.com/pydantic/pydantic-ai/blob/79e157e8b7bbea20d2354740e981478dd54dbb23/pydantic_ai_slim/pydantic_ai/models/openai.py#L1221)): "Whether to send the unique IDs of reasoning, text, and function call parts from the message history to the model... This can result in errors like `"Item 'rs_123' of type 'reasoning' was provided without its required following item."` if the message history you're sending does not match exactly what was received from the Responses API in a previous response, for example if you're using a history processor." A `TODO(v3)` in the code says it should be renamed `openai_send_item_ids` because it gates more than reasoning ids. The maintainer explained the rule in [#3230](https://github.com/pydantic/pydantic-ai/issues/3230) (2025-10-23): the API "now requires the input to match verbatim the previous output if any IDs are included."

**Text plus tool calls.** One `ModelResponse` holds `TextPart`, `ThinkingPart`, and `ToolCallPart` in order. Each part keeps its own item id. Commit [3530dcb](https://github.com/pydantic/pydantic-ai/commit/3530dcb2c67d36428134b13a94c7e6bcedfa110e) (2025-09-12) is titled "Store OpenAI Responses text part ID to prevent error with reasoning (#2882)". Newer models label assistant messages with a `phase` (`commentary` or `final_answer`). Pydantic AI keeps it in `provider_details` and sends it back. Its profile docstring says "dropping it can cause preambles to be interpreted as final answers and degrade behavior in long-running or tool-heavy flows" ([profiles/openai.py](https://github.com/pydantic/pydantic-ai/blob/79e157e8b7bbea20d2354740e981478dd54dbb23/pydantic_ai_slim/pydantic_ai/profiles/openai.py)).

**Bugs.**
- [#2870](https://github.com/pydantic/pydantic-ai/issues/2870) (2025-09): built-in tool calls were not parsed or sent back, so reasoning items lost their followers.
- [#2862](https://github.com/pydantic/pydantic-ai/issues/2862) (2025-09): a streaming regression in v1.0.3 crashed with `Cannot create a ThinkingPart with no content` on a reasoning item with no summary. This was on Azure; the maintainer cited Azure's docs: "reasoning summaries are not guaranteed to be generated for every step/request."
- [#3230](https://github.com/pydantic/pydantic-ai/issues/3230) (2025-10): `Item 'fc_...' of type 'function_call' was provided without its required 'reasoning' item`. A later commenter traced it to `previous_response_id="auto"` plus `truncation="auto"`: server-side history can be truncated between a reasoning item and its function call.
- [#4608](https://github.com/pydantic/pydantic-ai/issues/4608) (2026-03, open): through a gateway that spans several OpenAI orgs, replayed encrypted reasoning fails: `The encrypted content for item rs_... could not be verified. Reason: Encrypted content organization_id did not match the target organization.` (`invalid_encrypted_content`). The reporter saw it on about 0.05% of millions of requests. The maintainer refused to turn encrypted content off by default ("it will hurt performance significantly"). Auto-retry without ids is proposed in [PR #5482](https://github.com/pydantic/pydantic-ai/pull/5482) (open).
- [#5113](https://github.com/pydantic/pydantic-ai/issues/5113): with `store=True`, retries re-send the full history and create duplicate stored conversations.

## LangChain (`ChatOpenAI`)

**Architecture: one chat-shaped class, routed per request, history extended over time.** `ChatOpenAI` picks the endpoint on each call ([`_use_responses_api`, base.py L2012](https://github.com/langchain-ai/langchain/blob/864754c5e293fba981302408fa3e2cf2f5f2d889/libs/partners/openai/langchain_openai/chat_models/base.py#L2012)). It uses Responses when `use_responses_api=True`, when Responses-only settings are present (`reasoning`, `include`, `truncation`, `context_management`, `previous_response_id`, `text`, built-in tools), when the model name is in `_RESPONSES_API_ONLY_PREFIXES` (`gpt-5-pro`, `gpt-5.2-pro`, `gpt-5.4-pro`, `gpt-5.5-pro`, `gpt-5.6-sol`) or contains `codex`, or when the model starts with `gpt-6` and the payload has tools ([L763](https://github.com/langchain-ai/langchain/blob/864754c5e293fba981302408fa3e2cf2f5f2d889/libs/partners/openai/langchain_openai/chat_models/base.py#L763)). A broader rule for GPT-5.4 to 5.6 with function tools and reasoning is still an open PR, [#38860](https://github.com/langchain-ai/langchain/pull/38860) (opened 2026-07-15). It quotes the error that motivates it: `Function tools with reasoning_effort are not supported for gpt-5.6-luna in /v1/chat/completions. To use function tools, use /v1/responses or set reasoning_effort to 'none'.` The class docstring warns: "Model name can trigger Responses API routing ... independent of `base_url`."

**Format history.** `_compat.py` documents the evolution ([_compat.py](https://github.com/langchain-ai/langchain/blob/864754c5e293fba981302408fa3e2cf2f5f2d889/libs/partners/openai/langchain_openai/chat_models/_compat.py)). The original v0.3 format put one reasoning item in `AIMessage.additional_kwargs["reasoning"]` and the message id on `AIMessage.id`. The `responses/v1` format "retains information about response item sequencing and accommodates multiple reasoning items by representing these items in the content sequence". It became the default in `langchain-openai` 1.0.0. A LangChain staff answer on the forum says errors like `'web_search_call' was provided without its required 'reasoning' item` "can arise in the original LangChain implementation" and are fixed by `output_version="responses/v1"` ([forum thread](https://forum.langchain.com/t/langgraph-openai-responses-api-400-error-web-search-call-was-provided-without-its-required-reasoning-item/1740/2)).

**Conversion.** `_construct_responses_api_input` ([L4900](https://github.com/langchain-ai/langchain/blob/864754c5e293fba981302408fa3e2cf2f5f2d889/libs/partners/openai/langchain_openai/chat_models/base.py#L4900)) handles a plain chat-shaped assistant message (string `content` plus `tool_calls`) by emitting one id-less assistant `message` item and then one `function_call` item per tool call that is not already in the content blocks. Rich content blocks are passed through with their ids. Ids that LangChain generated itself (`lc_` prefix) are not forwarded: "the Responses API rejects them (expects `msg_...`)". With `store=False`, the docstring says: "Assistant message IDs (`msg_*`) are therefore omitted and reasoning blocks are dropped unless they carry `encrypted_content`." `store` is not sent unless set, and encrypted content is not requested unless the user adds it to `include`.

**Bugs and fixes** (from the [`langchain-openai==1.5.2a1` release notes](https://github.com/langchain-ai/langchain/releases/tag/langchain-openai%3D%3D1.5.2a1) and linked PRs):
- [#38372](https://github.com/langchain-ai/langchain/commit/792c1a743e4471990e96e818957b3299517e7255) (1.3.3): "drop response item ids when `store` is false". Replaying `rs_*`/`msg_*` ids with `store=False` crashed with `Item with id 'rs_...' not found`.
- [#39635](https://github.com/langchain-ai/langchain/pull/39635) (1.5.1, 2026-08-14): "preserve streamed encrypted reasoning". "OpenAI emits an empty placeholder on `response.output_item.added` and the final encrypted payload on `response.output_item.done`." LangChain JS had the same bug ([langchainjs#10844](https://github.com/langchain-ai/langchainjs/issues/10844)). A commenter added that dropping a reasoning item "can leave its `function_call` replaying an `fc_` id with nothing to pair it to." A maintainer replied that stripping ids instead means "dropping reasoning on subsequent turns, which could decrease performance."
- [#39715](https://github.com/langchain-ai/langchain/issues/39715) (open): converting back merges two distinct reasoning items into one, losing the second `id` and `encrypted_content`. This breaks a follow-up that has a function call.
- #38336 "drop `stop` from Responses API payload"; #39204 "preserve Responses `text` options"; #39209 "filter langchain-generated content block IDs"; #36725 "handle content blocks without type key in responses api conversion".
- [#35584](https://github.com/langchain-ai/langchain/issues/35584) (2026-03): a user reported `Unknown parameter: 'tool_choice.function'` on gpt-5.4 over Chat Completions. A maintainer could not reproduce it.
- LangChain JS: [#9072](https://github.com/langchain-ai/langchainjs/issues/9072) (2025-09) "stateless GPT-5 reasoning messages cause 400 ... reasoning without its required following item". JS has a `zdrEnabled` option that turns off features that depend on storage ([langchainjs PR #8090](https://github.com/langchain-ai/langchainjs/pull/8090)).

**Streaming.** `_convert_responses_chunk_to_generation_chunk` ([L5370](https://github.com/langchain-ai/langchain/blob/864754c5e293fba981302408fa3e2cf2f5f2d889/libs/partners/openai/langchain_openai/chat_models/base.py#L5370)) turns events into `AIMessageChunk`s with content blocks and `tool_call_chunks`. It keeps its own running block index from `output_index` and `content_index`. Summary parts are nested inside a reasoning block as `{"index": summary_index, ...}` and never used as the outer index. A code comment notes: "After several built-in tool calls the API can report a later `output_index`", so it records the first `output_index` seen per item id.

## LlamaIndex (`OpenAIResponses`)

**Architecture: separate class, thin conversion.** `OpenAIResponses` defaults to `store: bool = False` ([responses.py L224](https://github.com/run-llama/llama_index/blob/619d74664e8404612038bc15a1a40c686037277c/llama-index-integrations/llms/llama-index-llms-openai/llama_index/llms/openai/responses.py#L224)). `to_openai_responses_message_dict` ([utils.py L614](https://github.com/run-llama/llama_index/blob/619d74664e8404612038bc15a1a40c686037277c/llama-index-integrations/llms/llama-index-llms-openai/llama_index/llms/openai/utils.py#L614)) turns a `ChatMessage` into: reasoning items (only when `store` is true, sent as `{type, id, summary}` with no encrypted content), then an id-less assistant message if there is text, then `function_call` items.

**Bugs.**
- [#20333](https://github.com/run-llama/llama_index/issues/20333) (2025-12): reasoning then tool call fails. With `store=False`: `Item with id 'rs_...' not found. Items are not persisted when store is set to false`. With `store=True`: `Item 'rs_...' of type 'reasoning' was provided without its required following item`. [PR #20725](https://github.com/run-llama/llama_index/pull/20725) (2026-03) fixed it by omitting reasoning items when `store=False`. The PR author argued reasoning items "are not part of the conversational history". A maintainer disagreed, quoting OpenAI's guidance to include them when managing context manually.
- [#21124](https://github.com/run-llama/llama_index/issues/21124): the serializer dropped assistant text when tool calls were present, and passed tool arguments as dicts instead of JSON strings. The current code includes the text.
- [#19909](https://github.com/run-llama/llama_index/issues/19909): `FunctionAgent` + `OpenAIResponses` returned an empty string after a tool call when not streaming.
- [PR #21812](https://github.com/run-llama/llama_index/pull/21812): reasoning delta events were not handled, so "streamed reasoning tokens were silently dropped."
- [Discussion #21627](https://github.com/run-llama/llama_index/discussions/21627) (2026-05-12), titled "`OpenAIResponses` seems broken to a level that makes me think nobody is actually using it", reports wrong `strict` schemas and wrong conversion of tool calls and tool results.

## Continue (IDE coding agent, TypeScript)

The closest analog to a conversion layer over a chat-shaped history. Continue keeps chat-shaped `ChatMessage`s, with reasoning in separate "thinking" messages that carry `reasoning_details` (id, summary, encrypted content). `toResponsesInput` converts them ([openaiTypeConverters.ts L986](https://github.com/continuedev/continue/blob/5522c6f44ca0ac3528b37244818fbfa39b5af470/core/llm/openaiTypeConverters.ts#L986)). Requests always include `include: ["reasoning.encrypted_content"]` and do not set `store` ([OpenAI.ts L337](https://github.com/continuedev/continue/blob/5522c6f44ca0ac3528b37244818fbfa39b5af470/core/llm/llms/OpenAI.ts#L337)).

[PR #11785](https://github.com/continuedev/continue/pull/11785) (merged 2026-03-25) "Fixes three categories of OpenAI Responses API 400 errors (~100+ open issues)". The PR links about 60 issues titled like "Error: GPT-5 - 400". The fix adds `sanitizeResponsesInput` ([L926](https://github.com/continuedev/continue/blob/5522c6f44ca0ac3528b37244818fbfa39b5af470/core/llm/openaiTypeConverters.ts#L926)), which:
- removes reasoning without `encrypted_content` and strips the `id` from the `function_call`/`message` items after it;
- removes reasoning not followed by a `function_call` or message;
- removes `function_call_output` items with no matching `function_call`;
- keeps only `fc_`-prefixed ids on function calls, because of `Expected an ID that begins with 'fc'` errors caused by `msg_` ids leaking into `function_call` items.

## Haystack (`OpenAIResponsesChatGenerator`)

A separate generator class. `_convert_chat_message_to_responses_api_format` ([openai_responses.py L980](https://github.com/deepset-ai/haystack/blob/4b5dd70fde2a53f1913b6856d77c6f9c1def6720/haystack/components/generators/chat/openai_responses.py#L980)) emits, for an assistant message: reasoning items, then `function_call` items (with both `id` and `call_id`), then the text. That order differs from the model's usual output order, where text comes before the calls. Inference: whether OpenAI accepts this order with ids was not verified here. The code keeps two ids per tool call: `ToolCall.id` holds the `fc_` item id and `extra["call_id"]` holds the `call_` id. It filters reasoning fields down to `{id, type, encrypted_content, status, content}`, because event-level fields copied from streaming "the API rejects ... with 'Unknown parameter'". It has a dedicated `response.output_item.done` handler because "The done event carries the completed reasoning item, which includes encrypted_content". The finish reason is derived: `tool_calls` if any output item is a `function_call`, else `stop`, unless the response is incomplete.

## DSPy

DSPy has `dspy.LM(..., model_type="responses")`, which calls LiteLLM's native `litellm.responses()` / `aresponses()` ([litellm_engine.py L237](https://github.com/stanfordnlp/dspy/blob/25162c4fc05c2d2d019b0ffb5b6b2a9f315ec007/dspy/clients/engines/litellm_engine.py#L237)). The request is built from DSPy's chat-shaped request by its own dialect code, not by LiteLLM. Streaming on that path is refused: "LiteLLMEngine streaming currently requires model_type='chat'. Use the native Responses engine for Responses streaming." ([L161](https://github.com/stanfordnlp/dspy/blob/25162c4fc05c2d2d019b0ffb5b6b2a9f315ec007/dspy/clients/engines/litellm_engine.py#L161)). Because Responses has no `stop` or `top_k`, DSPy trims the reply on the client for `stop` and drops `top_k`, and records each as an "adaptation". The motivation, from a maintainer on [#8822](https://github.com/stanfordnlp/dspy/issues/8822) (2025-10-27): "litellm still has the issue of litellm.completion doesn't return reasoning summary with gpt-5, while the responses API works fine." Bugs: structured output did not survive the chat-to-Responses conversion ([#8872](https://github.com/stanfordnlp/dspy/issues/8872), [#9122](https://github.com/stanfordnlp/dspy/issues/9122) / [PR #9130](https://github.com/stanfordnlp/dspy/pull/9130): a Pydantic model passed as `text.format` is not valid). With `web_search`, output items came back as dicts and crashed the parser ([#8958](https://github.com/stanfordnlp/dspy/issues/8958)).
