# LiteLLM Responses support

## Bottom Line

Kiln's pinned LiteLLM (1.102.0 installed; 1.102.2 is identical in every Responses-related file) already has a working **chat-completions → Responses bridge** inside `litellm.completion()`. You switch it on per call with a model prefix (`openai/responses/<model>`, `azure/responses/<deployment>`, `openrouter/responses/<model>`) or globally with `litellm.route_all_chat_openai_to_responses = True`. Kiln keeps getting a chat-shaped `ModelResponse`: choices, tool_calls, usage with reasoning tokens, `response_cost`, and streaming chunks. LiteLLM also **auto-routes** some requests to `/v1/responses` with no change on the caller's side: OpenAI/Azure models that the cost map marks `mode: responses` (all `-pro`, `-codex`, `o1-pro`/`o3-pro`, deep-research), and **gpt-5.4+ (and gpt-6) requests that combine function tools with active reasoning**. In 1.102.0 it no longer drops `reasoning_effort` in that case. `litellm.responses()`/`aresponses()` exist too: they return `ResponsesAPIResponse` or a streaming event iterator, call OpenAI, Azure, OpenRouter, xAI and a few others natively, and bridge every other provider through `completion()`. The bridge has real gaps that a Kiln integration must handle. The worst is that, without streaming, a text-plus-tool-call turn comes back as **two choices**, and `choices[0]` has no `tool_calls`. Also: logprobs are dropped, `verbosity` is dropped (fixed in 1.104), and only the last reasoning item is kept.

## Key Findings

- **`responses()` signature and returns.** It takes the OpenAI Responses params (`input, model, include, instructions, max_output_tokens, reasoning, store, stream, text, text_format, tools, tool_choice, previous_response_id, ...`) plus LiteLLM kwargs. It returns `ResponsesAPIResponse` or `BaseResponsesAPIStreamingIterator`. Cost lands in `_hidden_params["response_cost"]`. Response ids are LiteLLM-encoded (base64-wrapped). See [responses-api-surface.md](./responses-api-surface.md) and the [LiteLLM /responses docs](https://docs.litellm.ai/docs/response_api).
- **Native providers (1.102.0 source, `utils.py:8789`):** openai, azure, openrouter, xai, github_copilot, chatgpt, litellm_proxy, volcengine, manus, perplexity, databricks (gpt only), hosted_vllm, fireworks_ai, bedrock_mantle (some models). Every other provider goes through the chat-completions bridge. OpenRouter's Responses endpoint is stateless and rejects `store: true` ([OpenRouter docs](https://openrouter.ai/docs/api/reference/responses/overview)).
- **Reverse bridge triggers** (`responses_api_bridge_check`, `main.py:1047`): the `responses/` prefix; the global flag (openai only); cost-map `mode: responses` (25 OpenAI and 25 Azure entries, **none for OpenRouter**); gpt-5.4+ with function tools and reasoning active on OpenAI or Azure. That last trigger also fires when effort is unset on the default OpenAI base or on Azure. An explicit `reasoning_effort="none"` keeps the request on chat. Azure deployments with custom names need the prefix. See [completion-to-responses-bridge.md](./completion-to-responses-bridge.md) and the [LiteLLM OpenAI docs](https://docs.litellm.ai/docs/providers/openai).
- **Param mapping verified on the wire.** system → `instructions`; tools → flat function tools (`strict: null` when not set); `response_format` json_schema → `text.format`; `reasoning_effort` (string or `{effort, summary}` dict) → `reasoning`; `max_tokens` → `max_output_tokens`; `include` and `store` pass through; assistant `reasoning_items` (with `encrypted_content`) are replayed as reasoning input items. **Dropped:** `logprobs`, `verbosity` (1.102), `stream_options`. **Never set by the bridge:** `store` (OpenAI's server default applies). See [probe-evidence.md](./probe-evidence.md).
- **`reasoning_effort` on the chat path.** `OpenAIGPT5Config` lets `xhigh` through only where the cost map says it is supported. It drops or rejects `minimal`/`low` where the map says unsupported. It flattens dict efforts. It **never validates `none`** on OpenAI ([#40472](https://github.com/BerriAI/litellm/issues/40472)). With Kiln's `drop_params=True`, unsupported levels are **silently removed**, so the provider default applies with no error (for example `gpt-5.5` + `minimal`, `gpt-5` + `xhigh`, `gpt-5.5-pro` + `low`). The same rules apply before bridging. The cost map and the LiteLLM docs disagree on `gpt-5.5` + `minimal`. OpenRouter receives a top-level `reasoning_effort`. See [reasoning-effort-translation.md](./reasoning-effort-translation.md).
- **Two-choice bug.** In non-streamed bridge responses where the model writes text and calls a tool, `choices[0]` has the text and `choices[1]` has the `tool_calls`. Reproduced in 1.102.0. Upstream [#43316](https://github.com/BerriAI/litellm/issues/43316) was closed on 2026-10-03, but the code is unchanged through 1.105.0rc1. The streaming path rebuilds a single correct choice.
- **Reasoning visibility.** `reasoning_content` on bridged responses is the reasoning *summary*, present only when a summary is requested and allowed. Raw reasoning text is dropped ([#40654](https://github.com/BerriAI/litellm/issues/40654)). Without streaming, only the last reasoning item is kept ([#43620](https://github.com/BerriAI/litellm/issues/43620)). The bridge does stream summary deltas, which the plain chat path does not ([#36992](https://github.com/BerriAI/litellm/issues/36992)).
- **Usage and cost.** Bridged responses map `reasoning_tokens` and `cached_tokens` into chat `usage` details and fill in `response_cost` (verified).
- **Routing depends on the cost map, and LiteLLM fetches that map remotely at import** unless `LITELLM_LOCAL_MODEL_COST_MAP=True`. So which models are auto-bridged can change without a package upgrade. Kiln does not set this.
- **Later versions.** 1.104.0 (latest stable, 2026-10-03) maps `verbosity` → `text.verbosity`, forwards non-enum efforts, and adds the Azure AI Foundry auto-route. See [versions-and-known-bugs.md](./versions-and-known-bugs.md) and the [v1.104.0 notes](https://docs.litellm.ai/release_notes/v1.104.0/v1-104-0).

## Open Questions / Gaps

- I did not call real OpenAI, Azure or OpenRouter endpoints. Probes show what LiteLLM sends and how it parses canned payloads, not how the providers respond. In particular, how OpenAI treats `strict: null` on Responses function tools is unverified.
- I could not see why #43316 was closed. GitHub API access to BerriAI/litellm is blocked in this session, and the issue page fetch did not show the closing event. The code diff says it is not fixed in any release up to 1.105.0rc1.
- Which is right about `gpt-5.5` + `minimal` (LiteLLM cost map: unsupported; LiteLLM docs: supported), and gpt-5.4's real default effort (map: `none`; bridge comment: medium), needs OpenAI's model docs. That belongs to subtopics 1 and 4.
- I did not establish exactly when the `openai/responses/` prefix and the gpt-5.4+ auto-route first shipped. The relevant entries are in the 1.85 and 1.102 release notes.
- I did not test the Azure bridge end to end. My mock returned the wrong shape for the Azure path, so only the route (`/openai/responses?api-version=...`) is verified.
