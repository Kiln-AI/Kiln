# Kiln adapter and public surface

What in Kiln's code a move to OpenAI's `/v1/responses` would change, and what must not change. Source: this repo at commit `579014ab` (on `main` `40ddbd84`), read 2026-10-30, with LiteLLM 1.102.0 installed. Claims are labelled **Read** (stated by code), **Observed** (run offline here, no network, every HTTP call intercepted by `respx`) or **Inference**.

## Bottom Line

Every agent model call in Kiln goes through `LiteLlmAdapter`: `build_completion_kwargs` builds one Chat Completions-shaped dict, and two near-copies of the tool loop (non-streaming `_run_model_turn` and streaming `AdapterStream`) send it with `litellm.acompletion` and read only `choices[0]`. A per-provider routing decision placed in `litellm_model_id`/`build_completion_kwargs` reaches both paths and every feature built on `adapter_for_task` (runs, evals, data gen, repair, synthetic user, task tools); extractors, embeddings, rerankers and connection checks are separate and unaffected unless routing is put in `get_litellm_provider_info` or made global. Kiln already uses LiteLLM's chat-to-responses layer today without knowing it: LiteLLM sends `gpt-5.4-pro` and `gpt-5.2-pro` on OpenAI direct to `/v1/responses`. Observed offline, that path keeps the public surface intact for simple replies, but it **silently drops a tool call when the reply also holds text** (non-streaming path), and **reasoning items survive within one run but are lost across runs**, because the saved trace type cannot hold them. Older app versions all read one remote model list, ignore unknown fields and drop providers with unknown enum values, so flipping `supports_function_calling` or adding the `max` level in published data reaches old clients that lack the routing code.

## Key Findings

- **One request builder, two response readers.** `build_completion_kwargs` ([litellm_adapter.py:862-953](../../../../libs/core/kiln_ai/adapters/model_adapters/litellm_adapter.py#L862)) feeds both `acompletion_checking_response` ([L580-594](../../../../libs/core/kiln_ai/adapters/model_adapters/litellm_adapter.py#L580)) and `StreamingCompletion` ([litellm_streaming.py:59-71](../../../../libs/core/kiln_ai/adapters/litellm_utils/litellm_streaming.py#L59)); the reply is read by `choices[0]` in two places (`acompletion_checking_response` and `adapter_stream._validate_response`, [adapter_stream.py:373-385](../../../../libs/core/kiln_ai/adapters/model_adapters/adapter_stream.py#L373)). Any reply-reading change must be made in both. Closed PR #1757 changed only the first. ([details](./adapter-request-response-path.md), [streaming](./streaming-and-ai-sdk.md))
- **Kiln already rides the conversion layer for Pro models.** Observed: `gpt_5_4_pro`/`openai` goes to `POST /v1/responses` with `input`, `instructions`, `reasoning: {effort}`, `temperature`; `store` unset; output, usage, cost and cached tokens came back in the shapes Kiln reads. Plain `gpt_5_4` goes to `/v1/chat/completions`. LiteLLM's bundled map marks `gpt-5.4-pro`, `gpt-5.2-pro`, `gpt-5-pro` as `"mode": "responses"`. ([§6](./adapter-request-response-path.md))
- **Silent wrong answer on text plus tool call.** Observed: when one Responses reply holds a text message and a function call, the non-streaming adapter returned the text as the final output after one call; the tool never ran and no error was raised. With hand-built chunks, `litellm.stream_chunk_builder` merged split choices into one, so the streaming path kept the tool call. ([§3](./adapter-request-response-path.md), [streaming §3](./streaming-and-ai-sdk.md))
- **Reasoning items: kept within a run, lost across runs.** Observed: on the second tool-loop call the bridge replayed the reasoning item (`id`, `encrypted_content`) because the live LiteLLM `Message.reasoning_items` stays in the message list. On a `prior_trace` continuation the item was gone. `litellm_message_to_trace_message` keeps only `content`, `reasoning_content`, `tool_calls` ([L1154-1204](../../../../libs/core/kiln_ai/adapters/model_adapters/litellm_adapter.py#L1154)), and `TaskRun.trace` validation drops any key the TypedDicts don't declare. Cross-run replay is used by multi-turn runs (`parent_task_run_id`), `return_on_tool_call` resume, and every synthetic-user turn. ([trace contract](./public-surface-and-trace-contract.md))
- **Public contracts to keep.** `invoke`/`invoke_returning_run_output` → `TaskRun`/`RunOutput`; `invoke_openai_stream` yields LiteLLM `ModelResponseStream` (Chat Completions chunks); `invoke_ai_sdk_stream` yields `AiSdkStreamEvent`s built only from `delta.reasoning_content`, `delta.content`, `delta.tool_calls`, `finish_reason` and a trailing usage chunk ([stream_events.py:209-295](../../../../libs/core/kiln_ai/adapters/model_adapters/stream_events.py#L209)); `KilnRunError.partial_trace`; LiteLLM exception classes used by retry logic. No in-repo production code calls the two streaming methods. ([public surface](./public-surface-and-trace-contract.md))
- **Request building has no OpenAI branch.** Read: OpenAI direct gets `reasoning_effort` as a string, `temperature`/`top_p` (dropped or not by LiteLLM's `drop_params`), `json_schema` response format without `strict`, and user tools with `strict: false` (added 2026-10-19 because Responses treats tools as strict by default). No `reasoning_summary`, `store` or `include` is sent, so OpenAI-direct runs never get reasoning text and all OpenAI-direct providers are `reasoning_capable=False`. Requesting summaries would add visible reasoning to runs and eval inputs. ([§2](./adapter-request-response-path.md))
- **`supports_function_calling` is a UI gate only.** Read: no adapter reads it; the model dropdown, models page and fine-tune page do. Inference: the `function_calling` structured-output mode, offered for every model, still sends `tools` + `reasoning_effort` on the affected models. ([model list §4](./model-list-and-remote-config.md))
- **Affected model-list entries.** Ten OpenAI-direct providers have `supports_function_calling=False` for this bug: `gpt-6.1-sol`, `gpt-6.1-terra`, `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4`. `max` is hidden on GPT-6.1 Sol and Terra direct because Chat Completions rejects it. GPT-5.4 mini/nano direct have no thinking levels (OpenRouter has them; cause not established). GPT-6/6.1 Pro models exist only on OpenRouter. ([model list §2](./model-list-and-remote-config.md))
- **Remote model list has no version gating.** Read: all clients from v0.19 fetch `kiln_config_v2.json`; `KilnModelProvider` ignores unknown keys; a provider with an invalid value in a known field (e.g. unknown provider name) is dropped with a warning; `adapter` (added v1.2.0) is ignored by older clients. Publishing goes through a human-merged PR to the `remote_config` branch. A new routing field is harmless to old clients; flipping existing fields is not. User-model `overrides` accept any new field automatically. ([model list §3](./model-list-and-remote-config.md))
- **Other LiteLLM callers.** Extractor: own `acompletion` call, no tools, no reasoning, reads `choices[0]`; unaffected by an adapter flag, affected by a global switch (file parts would go through the conversion). Embeddings, rerankers, Vertex/Bedrock connect checks: unaffected. Fine-tuning: no chat calls. The LiteLLM logging callback reads `.choices` and would only log "Could not print" on a native path. ([callers](./other-litellm-callers.md))
- **Tests.** Almost all adapter unit tests mock `acompletion_checking_response` with `(ModelResponse, Choices)`; none exercise LiteLLM's request translation except the `respx`-based Cloudflare tests, which are the template for offline wire tests (observed to work for `/v1/responses`). `test_litellm_adapter.py` uses bare `Mock()` providers 38 times, so a new boolean flag reads truthy there unless set. No OpenAI model is in the paid streaming or return-on-tool-call lists; the full thinking-level paid test asserts reasoning text for every OpenAI-direct level. ([tests](./tests-and-testing-a-routing-flag.md))

## Open Questions / Gaps

- **No paid calls.** All behavior was observed against `respx` fakes with hand-written Responses bodies. Real OpenAI replies were not seen. The thinking-level paid test's current pass/fail for OpenAI direct is unknown.
- **Streaming chunk shapes from the bridge** were not observed; the `stream_chunk_builder` check used synthetic chunks (LiteLLM subtopic).
- **Kiln's hosted chat server** is not in this repo, so whether it uses `invoke_ai_sdk_stream` (making AI SDK events a cross-release contract) is unconfirmed.
- **Why GPT-5.4 mini/nano direct have no thinking levels**, whether Chat Completions accepts `max` for GPT-6 Astra/Sol/Luna, and whether OpenAI rejects `function_calling` structured output with reasoning on the affected models: left to the history and OpenAI subtopics.
- **What old clients do** with a flipped `supports_function_calling` depends on each release's LiteLLM pin (history subtopic).
- Web sources were not used; the brief named the repo as the source.
