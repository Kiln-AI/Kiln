# Research Plan: Moving Kiln's OpenAI calls to the Responses API

## Goal

Gather everything needed to write the spec for a new project (`/spec new_project`): moving Kiln's LiteLLM adapter to OpenAI's `/v1/responses` endpoint for newer OpenAI models (GPT-5.4+, GPT-6+, and every OpenAI model released after them). Today Kiln calls `/v1/chat/completions`. OpenAI rejects function tools together with a reasoning effort other than `none` on that endpoint for GPT-5.4 and newer, so Kiln set `supports_function_calling=False` on those OpenAI-direct providers as a workaround. The research must explain the real bug behind that workaround, map what Kiln has to change, and give the facts needed to choose between LiteLLM's chat-to-responses conversion layer and LiteLLM's native Responses call.

Constraints the spec will hold to: Kiln's public interface should not change (adapter `invoke` methods, `TaskRun.trace` / `prior_trace` in OpenAI chat format, `invoke_openai_stream` yielding `ModelResponseStream`, `invoke_ai_sdk_stream`). Kiln pins `litellm>=1.102.0,<1.103` (`libs/core/pyproject.toml`); the installed source is at `.venv/lib/python3.13/site-packages/litellm/`.

Closed PR Kiln-AI/Kiln#1757 (branch `mike/openai-responses-routing`) was an earlier, non-engineer exploration. Treat it as a list of leads to verify, never as a source of truth.

## Focus Details

### Kiln adapter and public surface

Primary sources: this repo. Map the code a migration touches and the contracts it must keep. Cover: `libs/core/kiln_ai/adapters/model_adapters/litellm_adapter.py` (request building, `build_extra_body`, `response_format_options`, tool loop in `_run_model_turn`, `acompletion_checking_response` reading `choices[0]`, `usage_from_response`, trace conversion in `litellm_message_to_trace_message`), `adapter_stream.py` and `litellm_utils/litellm_streaming.py` (streaming tool loop, how the final response is rebuilt from chunks), `base_adapter.py` (public methods and their types), `stream_events.py` (AI SDK event conversion from chunks), `utils/open_ai_types.py` (trace types). List every other caller of LiteLLM chat completion in `libs/` and `app/` (extractors, embeddings, rerankers, eval judges, data gen, fine-tune, chat features, `utils/litellm.py` and `get_litellm_provider_info`) and say whether each would be affected. Cover the model list (`adapters/ml_model_list.py`: `KilnModelProvider` fields, which OpenAI-direct providers are affected, thinking levels hidden because of Chat Completions) and the remote model list (`adapters/remote_config.py`: how older app versions load providers, what they do with unknown fields, any version gating). Cover existing tests: unit tests for the adapter, paid tests (`--runpaid`), test helpers, and how a new routing flag would be tested. Out of scope: git history of the workaround (next subtopic), LiteLLM internals (LiteLLM subtopic), OpenAI docs. Web use is optional here; the repo is the source.

### History of the workaround

Primary sources: git history of this repo and Kiln-AI/Kiln pull requests on GitHub (GitHub MCP tools are scoped to Kiln-AI/Kiln). Find when and why `supports_function_calling=False` was set on each affected OpenAI-direct provider: use `git log -S` / `git blame` on the comment "OpenAI rejects reasoning_effort + tools on /v1/chat/completions" in `ml_model_list.py`, and read the referenced PRs (#1351, #1480, #1560, #1755, the closed #1562 about reasoning summaries, and the closed #1757). For each step, record the LiteLLM version Kiln pinned at the time (`git log -p libs/core/pyproject.toml`) and whether that version already routed these requests to Responses on its own. Quote the exact error OpenAI returned if it appears in PRs, tests or fixtures. Then establish the current state with the pinned LiteLLM (1.102.x): for each affected model id, what endpoint a tools-plus-reasoning request would hit, and what would break if the flag were removed today. Use a local fake HTTP server, since no OpenAI key is expected. Check whether `OPENAI_API_KEY` is set; if it is, ask before spending money and do not make paid calls without that. Also list the other Chat-Completions-driven workarounds in the model list (hidden `max` thinking level on GPT-6.1 Sol, missing reasoning summaries, temperature or top_p problems, Pro models that only work on Responses). Out of scope: designing the fix.

### LiteLLM Responses support

Primary sources: the installed LiteLLM source (`.venv/lib/python3.13/site-packages/litellm/`, version 1.102.0), LiteLLM docs (docs.litellm.ai), the BerriAI/litellm GitHub repo, its issues, and its release notes (read through web fetch tools; GitHub MCP tools cannot reach that repo). Cover both paths. (1) Native `litellm.responses()` / `litellm.aresponses()`: request and response types, streaming iterator, provider coverage, how cost and usage are reported. (2) The chat-to-responses conversion layer, which LiteLLM calls the responses API bridge (`litellm/completion_extras/litellm_responses_transformation/`, `responses_api_bridge_check` in `main.py`): every rule that routes a chat call to `/v1/responses` (`openai/responses/` model prefix, `mode: responses` in the model map, the automatic gpt-5.4+/gpt-6 tools-plus-reasoning rule, `litellm.route_all_chat_openai_to_responses`, reasoning summary aliases), how each chat parameter maps (tools and `strict`, `tool_choice`, `response_format` to `text.format` and its `strict` default, `reasoning_effort` as string or dict, `reasoning_summary`, `store`, `include`, `temperature`/`top_p`, `logprobs`/`top_logprobs`, `max_tokens`, `drop_params`, `allowed_openai_params`, `cache_control_injection_points`), how replies map back (choices, reasoning content, reasoning items and encrypted content round trip, usage, cost), and streaming translation. Document known defects with evidence, including: a reply with text plus a function call becoming two choices; streamed reasoning summary deltas using `summary_index` as the choice index; `strict` defaulting to false on `text.format`; `store` not being set. For each defect, check whether a newer LiteLLM release or open issue or PR addresses it. Also cover Azure OpenAI through the same layer. Out of scope: OpenAI's own documentation (next subtopic) and Kiln's code.

### OpenAI Responses API

Primary sources: OpenAI's official docs. Note: the built-in WebFetch tool cannot reach developers.openai.com or platform.openai.com from this environment; use the Exa or Tavily fetch tools instead. Start from https://developers.openai.com/api/docs/guides/migrate-to-responses and follow it to the function calling, reasoning, structured outputs, streaming, conversation state, and data controls guides, and the API reference for `POST /v1/responses`. Cover: request and response shape; function tool shape and strict default; `function_call` / `function_call_output` items and `call_id`; `text.format`; reasoning (`effort` values per model, `summary`, reasoning items, `include: ["reasoning.encrypted_content"]`, what happens when reasoning items are replayed by id with `store: false`); `store` defaults on both endpoints and data retention and ZDR implications; `previous_response_id` and the Conversations API; streaming event types; parameters not supported (`n`, `logprobs` details, `temperature`/`top_p` on reasoning models); caching and pricing differences. List which current models are Responses-only or have Responses-only features (tools with reasoning on GPT-5.4+, `max` effort, Pro models, reasoning summaries), and any statement about the future of Chat Completions. Briefly note how OpenRouter serves OpenAI models (Kiln's OpenRouter route for the same models works) and Azure's Responses support. Out of scope: LiteLLM behavior and other frameworks.

### Prior art

Primary sources: source code, changelogs, issues and docs of other LLM frameworks. Find how comparable libraries moved OpenAI calls to Responses while keeping a chat-style interface: OpenAI Agents SDK (Python), Vercel AI SDK (`@ai-sdk/openai` responses vs chat models), Pydantic AI (`OpenAIResponsesModel`), LangChain (`ChatOpenAI` `use_responses_api`), LlamaIndex, and any others that turn up. For each: whether they convert chat-shaped history to Responses items or switched to a native path; how they handle reasoning items between turns (stored ids vs encrypted content, `store` defaults); how they handle text plus tool calls in one reply; how they stream; and which bugs or user complaints followed the switch. The goal is lessons and pitfalls for Kiln's design choice between a conversion layer and a native path. Out of scope: LiteLLM itself, OpenAI docs, Kiln code.
