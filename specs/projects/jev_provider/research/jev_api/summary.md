# Research: TypeSafe AI System One API (Jev)

Source of truth: the Pydantic wire models shipped in the official `typesafe-sdk` 0.7.0 package on PyPI
(`typesafe_sdk/_schemas/models.py`, generated by datamodel-codegen from `https://api.typesafe.ai/openapi.json`),
plus `typesafe_sdk/_core/constants.py`. The docs site (docs.typesafe.ai) was not reachable from the research
sandbox, so the limits section below comes from third-party pages and is marked as unverified.

## Endpoint

- `POST https://api.typesafe.ai/v1/systemone`
- Headers: `Authorization: Bearer <TYPESAFE_API_KEY>`, `Content-Type: application/json`, `Accept: application/json`
- `GET https://api.typesafe.ai/v1/models` returns `{"models": [{"name", "description", "release_date"}]}`
- Env var convention used by the SDK: `TYPESAFE_API_KEY`, `TYPESAFE_BASE_URL` (default `https://api.typesafe.ai`)
- Default model alias: `jev-latest`. Other names seen: `jev-1.13.0`, `jev-preview`.
- SDK default HTTP timeout: 10s. Responses are fast (no token generation).
- Error body on 422: `{"detail": [{"loc": [...], "msg": "...", "type": "...", "input": ..., "ctx": ...}]}` (FastAPI style).
- Rate limiting: `retry-after` / `retry-after-ms` headers; request id in `x-typesafe-request-id`.

## Request body

```json
{
  "state": <string | object | array>,
  "model": "jev-latest",
  "questions": { "<name>": <Question>, ... }
}
```

- `state`: the content every question refers to. Any JSON: string, object, or array.
- `questions`: non-empty dict keyed by caller-chosen names. The response uses the same names.

### Question types (discriminated on `type`)

| type | fields | notes |
|---|---|---|
| `noul` | `instructions?: JSONContent`, `criteria?: {"true"?: JSONContent, "false"?: JSONContent}` | yes/no statement or question |
| `choice` | `instructions?: JSONContent`, `criteria: {label: JSONContent \| null}` | pick one label; `null` description means "interpret by name" |
| `score` | `instructions?: JSONContent`, `criteria: [JSONContent, ...]` (min 1) | ordered rubric; position in list is the level, starting at 0 |

`JSONContent` = string, object, or array. `instructions` is optional on every type.

## Response body

```json
{
  "model": "jev-1.13.0",
  "answers": { "<name>": <Answer>, ... },
  "usage": { "input_tokens": 120, "output_tokens": 12 }
}
```

### Answer types (discriminated on `type`, matches the question's type)

| type | fields |
|---|---|
| `noul` | `noul: float` in [0,1], probability of yes/true. No confidence field. |
| `choice` | `choice: str` (highest-probability label), `confidence: float` in [0,1], `probabilities: {label: float}` summing to ~1 |
| `score` | `score: float` (probability-weighted expected level, may be non-integer), `confidence: float`, `legend: {"0": desc, "1": desc, ...}`, `probabilities: {"0": float, ...}` keyed by level as a string |

## Limits

Verified against the primitives pages of the docs (fetched later via a different route):

- Score: at least 2 and at most 10 levels.
- Choice: up to 255 options.
- Noul: the docs list `instructions` as required (the SDK models mark it optional; treat it as required).
- Questions in one request are evaluated in parallel and all see the same state; adding questions barely changes latency but each costs tokens.

Unverified, from third-party write-ups only:

- ~32 questions per request
- ~32k tokens for state plus the longest question; ~64k per request
- Pricing is per input token; output tokens are free.

The API returns 4xx with a descriptive error when a limit is exceeded, and Kiln surfaces that error verbatim.

## Behavioral notes

- No system prompt concept. Docs recommend putting content and supporting facts in `state` (as a JSON object for anything non-trivial) and putting the judgment to make in each question's `instructions`.
- Jev always answers every question; there is no "abstain".
- Score `score` is an expected value; to emit a discrete level use argmax over `probabilities`.
- LiteLLM supports Jev only as a proxy pass-through route (`/typesafe/v1/systemone`), not in the Python SDK. A native HTTP client is required.
- The official Python SDK (`typesafe-sdk`) depends on `httpx2` and pydantic v2. The API is one POST, so a small native client is lighter than adding the SDK.
